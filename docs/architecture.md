# Architecture

The core owns SQLite tasks, input events, routing decisions, delivery attempts, reports, and audit records. Router, agent runtime profile, and session transport are separate layers:

```text
submit -> durable input -> Router -> reply | new task | follow-up
                                           |
                         task branch/worktree + one persistent worker
                                           |
                   WorkerTransport (Herdr first) -> agent kind + argv
                                           |
                         correlated ack/progress/final reports -> SQLite
```

`src/adapters.ts` defines the `WorkerTransport` contract: `create` returns an opaque reference, `start` launches the independently selected agent, `resume` launches it again on a saved native session, `inspect` returns opaque instance/session identities, transport readiness and whether the worker was `rebound`, `probe` says whether the saved pane is missing, an empty shell (with its cwd) or occupied by an agent (with its session), `pin` records the worker's resume command with the transport, `send` transmits an input envelope, and `close` ends the worker only if its saved instance still matches (`closed`, `absent`, or `unverified` and left alone). Two error classes carry meaning to the core: `TransportUnavailable` (the server cannot be reached; says nothing about workers) and `WorkerAbsent` (no agent, or no reported session yet, in the saved pane; not an identity conflict). The core stores these identities and never interprets Herdr pane syntax. A future adapter must preserve intent/result boundaries and all uncertainty semantics. Merely replacing terminal commands is insufficient if identity or acknowledgement capabilities differ.

The Herdr adapter reads `.result.root_pane.pane_id` from workspace creation, uses that pane as the target rather than a live alias, and records `.result.agent.terminal_id` plus canonical `agent_session:{agent,kind,value}`. Both `id` and `path` session kinds are opaque strings. Every inspect checks agent kind and foreground/current cwd against the task worktree. Every dispatch checks instance/session identity and requires interactive readiness plus idle/done. Those states gate input only; they never establish task completion. Changed identity fails closed.

## Worker continuity

A Herdr server restart keeps pane IDs but gives every pane a new `terminal_id`, and Herdr resumes each agent on its reported native session. The adapter therefore accepts a changed terminal only when a saved session exists and the pane, agent kind, cwd and session all match; that inspection is `rebound`. The core records it (`rebind` audit, new instance) and, because the process that held any in-flight turn is gone, moves that turn's event and deliveries to `uncertain` with an `interrupted` audit. It never resends. A report for an uncertain event is still accepted, and `resolve` remains the operator's decision. Herdr briefly reports the persisted identity before the resumed process runs; dispatch still waits for interactive readiness and idle/done.

Reconcile treats `TransportUnavailable` as an outage: it audits `transport-offline` once per process, stops inspecting, and the pass only routes. Scheduling hits the same error and stops. A `WorkerAbsent` result is recorded in `tasks.error` with a `worker-absent` audit and interrupts an in-flight turn, but leaves `provision` at `started`; once a strict inspection succeeds again the error clears. Only a fresh launch waits (up to 15 s) for the agent to report its session.

Herdr's native restore runs only the bare resume command (`codex resume ID`), so launch arguments such as `--sandbox` and `--add-dir STATE` would be lost. After every verified launch, respawn, manual recovery and rebind, the core asks the adapter to `pin` the pane: `pane report-agent-session --source switchyard --agent KIND --agent-session-id ID PANE -- KIND <resume argv> <worker args>`. Herdr stores this as the pane's `agent_resume` and uses it on the next restore, leaving the agent's own `agent_session` untouched; a later session report by the agent does not clear it. A pin failure is audited (`pin-failed`) and otherwise ignored.

`recover --task ID` re-verifies a frozen or started task read-only against its saved pane and session, then rebinds if the terminal changed. `recover --task ID --respawn` requires a saved session, a valid worktree and provision `started` or `unknown`. It probes the saved pane: an agent with the saved session is just re-verified; any other agent or session is refused; a shell must be in the task worktree; a missing pane gets a new background workspace. The respawn audits `respawn-start` and interrupts any in-flight turn, then follows the launch write-ahead stages (`creating -> created` if needed, `starting -> started`). Any failure, including an agent that reports a different session, freezes the task as `unknown`. Token, branch, worktree and saved session never change.

Launch stages are persisted before side effects: `new -> worktree -> creating -> created -> starting -> started`. Git worktree creation can reconcile by exact registered path/branch; Herdr create/start without a known successful result becomes `unknown` on restart. A known created pane can continue start once; an interrupted start cannot repeat. All external processes receive argv arrays without shell interpolation. Structured Router output is validated before a transaction creates a task or assigns an event.

Outbox state precedes prompt submission: delivery `sending` and task `inflight` are committed together. Success becomes `sent`, a correlated report becomes `confirmed`, and unobserved outcomes become `uncertain`. Process failure alone does not prove absence of delivery. Every attempt preserves the stable event ID; explicit operator-approved retry appends a new attempt. Worker receipt/final reports can race the send result safely: send callbacks only update still-`sending` records. Reports transact their token/current-input checks and event/task updates. A final report is the only automatic turn release.

The supervisor lock is acquired transactionally with owner UUID, PID, hostname and timestamp. Only a demonstrably nonexistent same-host PID can be removed. A live/permission-inaccessible PID blocks takeover; there is no lease expiry that lets a paused previous owner resume dispatch after losing ownership. Crash recovery runs after lock acquisition. Report/submit commands may write concurrently; SQLite immediate transactions serialize their changes. This is local-only coordination, not a distributed lease.

## Task lifecycle and reclamation

`tasks.lifecycle` is separate from turn `status`: `open -> closing -> closed` for close, and `open|closing -> dropping -> closed -> dropped` or `closed -> dropped` for drop. `closing`/`dropping` always mean teardown (pane and worktree) is unfinished; `closed` means only the branch remains. Only `open` tasks are Router candidates, accept explicit follow-ups, reconcile, or schedule. `close`, `drop`, and `gc --merged` write rows to `requests` (task, action, options, `pending|done|rejected|failed`). The supervisor-lock holder applies them at the start of each pass, after reconcile and before routing. A CLI invocation applies them itself when it can take the lock, and otherwise waits while `serve` does. Requests for the same action and options are idempotent; a different pending request for the task is refused.

Each request is validated read-only first: active or queued input, dirty worktree, unregistered directory, unmerged branch, branch checked out elsewhere, and transport preflight. A failure here is `rejected` with no side effect. Next, one transaction writes `closing`/`dropping` and, with `--abandon`, marks the task's open inputs and deliveries `abandoned` and clears `inflight`. Only then does it call transport `close`, `git worktree remove` (forced only with `--discard-changes`), and, for drop, `git update-ref -d refs/heads/BRANCH SHA`. That deletes the branch only if it still points at the validated commit. A failure after the intent is `failed`. The task stays out of scheduling, and rerunning the command resumes from the recorded lifecycle; every teardown step tolerates having already happened, and a drop interrupted after teardown never calls the transport again.

Merged means `merge-base --is-ancestor`, or `git cherry` reporting no unique commits. `gc --merged` recomputes eligibility from live Git and status and submits ordinary drop requests without discard flags, so each one is validated again under the lock. Disk usage counts allocated blocks of regular files once per inode. The disk guard compares the minimum available space across the state, worktree, and repository filesystems with `minFreeMb` before every provision and dispatch. The dispatch transaction re-checks lifecycle, `inflight`, and pending requests, so a close cannot race a new turn.

## Human CLI

`sy` is the same CLI as `switchyard`; the human layer adds discovery, short task numbers, read models and routing feedback on top of the engine without changing its write paths.

- **State discovery** (`src/locate.ts`). Order: `--state`, `SWITCHYARD_STATE` (set in every worker pane created by Switchyard, with `SWITCHYARD_TASK`), a walk up from the current directory for `.switchyard/state.db` or for a `STATE/worktrees/task_*` directory whose `STATE/state.db` exists, then the per-repository default `$XDG_STATE_HOME/switchyard/<basename>-<sha256(root)[0:10]>` (`~/.local/state` without XDG) if it is initialized. The root is the main checkout, found from linked worktrees through `--git-common-dir`. Discovery never creates state; `init` is the only command that does, and it now defaults `--repo` to that root and the state to the default path.
- **Task numbers.** `tasks.num` is a unique short number assigned in the routing transaction (`MAX(num)+1`). The additive migration backfills existing tasks in `created, rowid` order before creating the unique index. `resolveTask` accepts `#N`, `N`, an exact ID or a unique ID prefix of at least four characters; ambiguity is an error, never a guess.
- **Read models** (`src/view.ts`). Read-only: no transaction, transport or Git call. `classify` puts each task in one bucket in the order a human must act: a pending request is in progress; an unfinished `closing`/`dropping`, a frozen launch, an uncertain input, a task error (an absent agent points to `recover N --respawn`) or a disk-guard hold needs you; an in-flight turn or queued input is in progress; the last final report then decides blocked (needs you), ready (review) or failed. `inbox`, `detail` (timeline of inputs, deliveries, reports and audits, plus next steps) and `inputView` back both the text renderers and `--json`; status, history and report output keep their existing JSON.
- **Lock roles.** `supervisor.owner` is `serve:…`, `run:…` or `cli:…`. Only a live `serve` holder counts as a running supervisor; a second `serve` is refused, while `serve` waits for a short `cli`/`run` holder to finish instead of failing. Liveness and takeover rules are unchanged.
- **Routing feedback.** `sy "text"` persists the input exactly like `submit`, then: if no live process holds the lock, it takes a `cli` lock and runs `routePending` once; otherwise it polls until the running holder has routed the input (Router timeout plus 5 s). Either way exactly one process calls the Router, and the input is durable before any call. `#N text` targets the task directly and never calls the Router. `submit` remains persist-only.
- **Recovery while serving.** `recover TASK` and `recover TASK --respawn` become `requests` rows (`recover`/`respawn`) when the lock is held. The lock holder applies them in `applyRequests` through `applyRecovery`, between reconcile and routing, so they never race a dispatch or a lifecycle change; a failure marks the request `failed` and audits `recover-failed`/`respawn-failed`. A task with a pending request is not dispatched, and `reverify`/`respawn` exclude only their own request when checking that. While Herdr is unreachable the request stays pending. Explicit `--ref/--session` adoption still requires exclusive access. `resolve` records the operator's decision in one transaction without the lock; it reconciles first only when it can take the lock, since a running supervisor already reconciles every pass.
- **Supervisor output.** JSON `serve` prints a status line only when it differs from the previous one. Text mode (`sy up`, `serve --format text`) compares `snapshot`s and prints one line per bucket or reason change, plus transport offline/online transitions and Router replies or routing errors. A change into needs-you, review or failed can raise a notification through the transport's `notify(title, body)` (Herdr: `notification show TITLE --body BODY --sound request`). Notifications are best effort: a failure is logged and never affects state. `up` enables them by default; `serve` only with `--notify`.

## Adapter assumptions and limits

Checked against installed Codex 0.165 help and Herdr 0.8 protocol 19 bundled schema; reclamation and continuity were also run live against Herdr 0.9.5 by `npm run smoke:herdr`, with a deterministic stand-in agent detected as `codex`. No real Codex/Claude worker or paid model call was used to validate this repository. Offline subprocess fixtures validate command construction, JSON envelopes, alternate profiles, state transitions and recovery. Real-agent reliability also depends on configured integration hooks, provider login, trust prompts, permissions, model behavior and the worker following reports. A report's evidence is recorded, not independently verified.

The built-in Codex Router uses supported structured non-interactive output and installed authentication. See [official non-interactive documentation](https://learn.chatgpt.com/docs/non-interactive-mode). It is intentionally stateless; business state stays in SQLite. The Router does not need the Worker's provider. A command Router can be any process, including a rule-based or remote-model wrapper, so long as classification is side-effect free.

Terminal pane/session inspection cannot prove an arbitrary process's identity cryptographically. Saved instance, session, agent kind, cwd and opaque stable pane reference together are the available Herdr checks. A dead agent is brought back only on its own saved session, by Herdr's restore or an explicit `recover --respawn`; Switchyard never starts a fresh conversation for an existing task. Explicit adoption can bind an initially unobserved launch only after operator verification. Replacing an already saved worker identity requires future generation rotation, not blind token reuse.

Final user acceptance, branch merging, interrupting an agent mid-action, token rotation, report redaction, automatic task expiry or reclamation, external cache cleanup, and daemon installation are out of scope. Stop supervision gracefully. The only pane close is the verified one requested through `close`/`drop`/`gc`; no `server stop`, agent kill, focus change, or unrelated terminal control is performed. The only other pane writes are `agent start` for a respawn into a verified shell pane and the resume-command pin. State/config must stay at their initialized paths; copy/move migration is not implemented. Schema changes are additive and applied in place on open (v0.1 state gains `lifecycle` and `requests`, and earlier state gains `tasks.num`, backfilled in creation order); the schema is not yet promised stable.

## Other transports: feasibility research

**tmux is feasible** as a session/message transport. Its official [control mode](https://github.com/tmux/tmux/wiki/Control-Mode) exposes command responses and pane output streams. It would need a `WorkerTransport` implementation with stable session/pane references, runtime detection/readiness, and the same explicit report protocol: terminal output or idle detection still cannot acknowledge business completion. This alternative is researched, not implemented or live-tested here.

**Headless is feasible**, but means replacing the terminal with process supervision and a provider protocol adapter. Codex [app-server](https://learn.chatgpt.com/docs/app-server) supports thread/turn lifecycle APIs; Claude's [headless interface](https://code.claude.com/docs/en/headless) supports structured streams and resumption. These are different protocols that require provider-specific handling, durable identities and crash semantics. They do not require Herdr/tmux, but they still require a transport and lifecycle implementation. v0.1 ships Herdr only, keeping this boundary explicit for later work.
